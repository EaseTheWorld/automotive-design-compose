1부. Android 공식 문서로 보는 SDV Display Safety 아키텍처

출처: Display Safety 개요 · DriverUI 아키텍처 · Safety Design Toolchain

1-1. 왜 Display Safety인가? (3대 핵심 컴포넌트와 Dual-VM 분리)

ISO 26262 ASIL-B + QM 공존

최신 콕핏 도메인 컨트롤러(Cockpit Domain Controller)는 클러스터(계기판)와 IVI(인포테인먼트)를 하나의 통합 디스플레이 환경으로 결합합니다. 하지만 Android(AAOS) 단독으로는 Cold Boot 즉시 표시(Rapid Boot)와 기능 안전(ISO 26262 ASIL-B)을 보장하기 어렵기 때문에, AOSP Display Safety는 시스템을 두 개의 Guest VM과 3대 소프트웨어 컴포넌트로 분리합니다.

▲ [AOSP 공식 그림] 클러스터와 IVI가 결합된 현대적 DriverUI 화면 예시

▲ [AOSP 공식 그림] Guest VM2 (SDV Media: HAR + Safety Monitor) vs Guest VM1 (SDV-IVI: DriverUI)

Guest VM 2 · SDV Media (Rapid Boot VM)

① HAR (High Availability Renderer)

🎯 핵심 목적: 고가용성(High Availability) & Cold Boot 즉시 표시
  • 왜 별도 VM인가? Android는 부팅에 15~30초가 걸리고 앱/시스템 크래시로 재부팅될 수 있음. 반면 HAR는 초경량 VM 위에서 시동 직후 1~2초 내(Cold Boot) 즉시 켜지고 절대 죽지 않음
  • 언어/렌더러: 가비지 컬렉션(GC) 없는 순수 Rust + Impeller GPU 렌더러
  • 역할: 속도, RPM, 경고등(Telltales), 후방 카메라 및 Android 부팅/장애 시 Fallback 배경 렌더링
Guest VM 1 · SDV-IVI (Android VM)

② DriverUI (Android System App)

🎯 핵심 목적: 풍부한 인포테인먼트(Rich IVI 생태계)
  • 프레임워크: AAOS ClusterHomeManager (Cluster 2 API) + Automotive Design for Compose
  • 역할: HAR가 그리는 안전 요소를 제외한 나머지 전체 클러스터 화면(미디어, 전화, 내비게이션, 날씨 등) 렌더링
  • 부팅이 완료되면 주기적으로 HAR에 HeartbeatRequest RPC를 전송하여 생존 상태를 알림
Guest VM 2 · ASIL-B 무결성 검증

③ Safety Design Toolchain & Monitor

🎯 핵심 목적: 기능 안전 무결성(Safety Integrity · ASIL-B)
  • 핵심 가치: HAR가 빠르게 그린 화면이 GPU/셰이더 버그로 깨지지 않았는지 최종 프레임버퍼 픽셀을 감시하여 ASIL-B 달성
  • 단일 Figma 디자인(.dcf)에서 안전 중요 노드(Telltales) 좌표와 정답 이미지를 추출해 ISO-26262 TCL-3 등급의 검증 코드 생성

💡 한눈에 구분하는 3대 컴포넌트의 존재 이유 (Availability vs Safety vs Richness)

AOSP 문서에서 DriverUI와 HAR는 둘 다 QM(Quality Management, 일반 품질 등급)으로 분류되지만, 존재 이유(비기능 요구사항)가 완전히 다릅니다!

구분 책임 영역 Cold Boot 부팅 속도 런타임 안정성 ISO 26262 등급 역할
DriverUI (Android VM) 기능성 (Rich Ecosystem) 느림 (15~30초 소요) 무거운 OS·앱 크래시/GC 지연 가능 QM (비안전 인포테인먼트)
HAR (SDV Media VM) 고가용성 (High Availability) 초고속 (시동 후 1~2초 내 즉시 표시) Android가 죽어도 무중단 60fps 렌더링 QM(B) (렌더링 수행 채널)
Safety Monitor (VM2) 무결성 검증 (Safety Integrity) HAR와 함께 즉시 기동 GPU 없이 CPU로 픽셀만 독립 검사 ASIL B(B) (독립 픽셀 감시 채널)

1-2. HAR + DriverUI 화면 합성(Blending)과 Heartbeat 메커니즘

Hardware Display Plane Compositing

▲ [AOSP 공식 그림] 상단 HAR (SDV VM) + 하단 DriverUI (AAOS IVI VM) → Hypervisor / SoC Display Controller가 하나의 화면으로 합성

💓 Heartbeat 기반 투명도(Transparency) 제어

HAR의 하드웨어 디스플레이 플레인은 안전 중요도 때문에 항상 Android IVI 플레인 위(Top Layer)에 위치합니다.

  • 정상 상태 (Heartbeat 수신 중): DriverUI가 주기적으로 HeartbeatRequest RPC를 보내면, HAR는 플레이스홀더/배경을 제거하고 Android 출력 영역을 완전 투명(alpha = 0.0)으로 비워 하단 DriverUI가 투과(See-Through)되게 합니다.
  • 장애/부팅 상태 (Heartbeat 끊김): DriverUI로부터 Heartbeat가 끊기면 HAR가 즉시 배경 영역을 불투명(alpha = 1.0)하게 채우고 자체 안전 UI와 플레이스홀더를 표시합니다.

🔍 공식 문서가 강조하는 Alpha 합성 및 Cross-VM 주의사항

  • Alpha Punch-Through: HAR가 그리는 게이지/3D 요소는 반드시 alpha = 1.0 (0xFF)이어야 하며, 나머지 영역은 alpha = 0.0으로 클리어되어야 하단 Android 레이어가 보입니다.
  • Cross-VM 디버깅 한계: HAR(sdv_media_har_cf)와 Android IVI(sdv_ivi_cf_ds)는 서로 다른 Guest VM에서 돌기 때문에, Android에서 adb shell dumpsys SurfaceFlinger를 실행해도 상단 HAR 레이어는 보이지 않습니다.

1-4. [심층 해설] Safety Design Toolchain & Safety Monitor란 무엇인가?

ISO 26262 ASIL-B & TCL-3

자동차 기능 안전 표준(ISO 26262 ASIL-B)에서는 "차량 버스에서 브레이크/안전벨트 경고등 신호(ON)를 보냈을 때, 렌더러 버그나 레이어 가림 없이 실제 화면 픽셀에 경고등이 제대로 찍혔는가?"를 검증해야 합니다. 이를 위해 AOSP는 그리는 프로세스(HAR)와 검사하는 프로세스(Safety Monitor)를 분리하고, 동일한 Figma .dcf 파일에서 검사 기준(좌표 + 정답 픽셀)을 자동 추출하는 Safety Design Toolchain을 제공합니다.

▲ [AOSP 공식 그림] Safety Design Toolchain 파이프라인: Figma .dcf + Config.json → Safety Design Compiler → 엔지니어 육안 검수(HTML Report) 및 SHA-256 승인 토큰 → MISRA-C Safety Monitor 빌드

Step 1 · 입력 정의
.dcf + Config.json

차량 신호 이름과 Figma 경고등 노드를 매핑합니다.
예: "seatbelts": "#cluster/telltale/no-seatbelt"

Step 2 · Design Compiler
Headless Impeller 추출

.dcf를 렌더링하며 각 경고등의 정확한 Bounding Box 좌표(data.json)와 조각 이미지(Golden Image PNG)를 추출합니다.

Step 3 · HRR 승인 (TCL-3)
Human-Readable Report

안전 엔지니어가 HTML 리포트의 좌표·스크린샷을 육안 검수 후 approve-hrr로 SHA-256 승인 토큰을 발급합니다.

Step 4 · 코드 생성 & 감시
har_safety_monitor

승인된 Golden Image를 C 헤더/바이너리로 컴파일하여, 런타임에 실제 화면 픽셀과 실시간 대조합니다.

🛡️ ISO 26262-9 ASIL Decomposition (QM(B) + ASIL B(B))

수백만 줄에 달하는 GPU 드라이버와 Impeller 그래픽 스택 전체를 ASIL-B로 인증받는 대신, 국제 표준 ISO 26262-9 (Clause 5)의 분해 원리를 적용합니다:

  • QM(B) 채널 — HAR: 복잡한 GPU/Impeller를 사용해 시동 후 1~2초 내 고가용성 렌더링 수행
  • ASIL B(B) 채널 — Safety Monitor: GPU 없이 순수 CPU로 프레임버퍼의 경고등 픽셀만 독립 검증
  • 하드웨어 Watchdog: 만약 VM2 자체가 멈추면 외부 Safety MCU / Display Controller가 타임아웃 감지
📚 공식 레퍼런스: AOSP Safety Design Toolchain (TCL-3 / ASIL-B) · ISO 26262-9 ASIL Decomposition

🔍 정적 Golden Image 픽셀 비교 원리 & Mismatch 감지 시 동작

  • 빌드 타임 1회 생성 & C 헤더(.h) 상수 내장:
    Golden Image는 주행 중(런타임) 차량 데이터가 바뀔 때마다 새로 만드는 것이 아닙니다. 검사 대상인 Telltale 아이콘들은 ON/OFF 두 상태만 가지므로, 빌드 타임에 각 아이콘이 켜졌을 때의 정적 이미지를 딱 1장씩만 추출해 C 헤더 파일 상수로 바이너리에 내장합니다. 런타임에는 차량 신호(ON/OFF)에 따라 내장된 Golden Image와 일치하는지만 대조합니다.
  • 고정 좌표 ROI Crop & Alpha Masking:
    전체 화면(1920×720)이 아니라 data.json에 정의된 경고등 사각형(예: X:72, Y:674, 45×45)만 잘라내며, 투명 배경 픽셀(alpha == 0)은 무시하고 불투명 아이콘 픽셀만 대조합니다.
  • 오류(Mismatch) 감지 시 동작 (AOSP 공식 문서 기준):
    공식 문서상 레퍼런스 har_safety_monitor의 역할은 "Mismatch detection: Logs an error if there is a mismatch between what is expected based on vehicle data and what is visible on screen"으로 명확히 한정되어 있습니다. 즉, Safety Monitor는 화면을 직접 수정하지 않는 순수 Read-Only 감시 프로세스로서 픽셀 불일치 발생 시 에러를 기록·보고하는 역할만 수행합니다.

Part 2 · POC Simulation & Architecture Comparison

2부. 단일 Android 개발 환경 제약을 고려한 DesignCompose POC 구현 및 비교 분석

일반 Android 앱 개발 환경(단일 VM 에뮬레이터)에서는 Hypervisor나 SDV Media VM(Rust + Impeller)을 직접 구동할 수 없습니다. 따라서 현재 Android 개발 환경에서 검증 가능한 핵심 아키텍처(단일 .dcf 분리 렌더링, Rust dc_layout, HAR Data-Driven 제약, See-Through & Failover)를 최대치로 시뮬레이션했습니다.

2-1. [핵심 요약] 공식 양산 Dual-VM 아키텍처 vs 본 POC 비교 (Same · Similar · Different)

동일 (Same) 유사 (Similar) 차이 (Different / 환경 제약)
아키텍처 영역 비교 판정 1부: AOSP 공식 Dual-VM (Production SDV) 2부: 본 DesignCompose POC (Single Android VM)
1. 디자인 소스 (.dcf) 동일 (Same) 단일 Figma 문서를 직렬화한 .dcf 번들을 VM1(DriverUI)과 VM2(HAR)가 공유 100% 동일한 공식 .dcf 파일(CuF1b1eAIukB6YszX6B5OZ.dcf)에서 #HAR-stage와 #android-stage를 각각 로드
2. Rust 파서 & 레이아웃 엔진 동일 (Same) Rust 크레이트(dc_bundle, dc_layout)가 .dcf 노드 트리와 레이아웃 계산 JNI를 통해 동일한 Rust dc_bundle + dc_layout 엔진이 레이아웃과 Variant 트리를 계산
3. HAR의 Data-Driven 인터페이스 동일 (Same) HAR는 Jetpack Compose가 없으므로 스칼라 신호(속도, 경고등)와 Variant 상태만 주입받음 ClusterDualVmStage.kt의 harStage에서 @Composable 교체 람다를 전면 배제하고 오직 @Design 데이터와 @DesignVariant만 허용
4. 투명 배경 & Failover 레이어 구조 동일 (Same) #HAR-stage는 기본 투명(alpha = 0.0)이며, Heartbeat 상실 시 불투명 배경(#heartbeat=off) 표시 해킹(BlendMode) 없이 .dcf 내부의 BackgroundLayer(#heartbeat=off) 가시성 제어만으로 Native See-Through 및 Failover 구현
5. 테마(Variable Mode) 동시 전환 동일 (Same) Figma Variable Collection(Dark / Light)을 통해 HAR와 DriverUI 테마를 동시 변경 DesignVariableModeValues로 Dark / Light 모드를 두 Stage에 동시 적용
6. 2-Plane 디스플레이 합성 유사 (Similar) Hypervisor / SoC Display Controller가 하단 IVI Plane과 상단 HAR Plane을 하드웨어 합성 단일 화면의 2-Layer Z-Order Stack에서 하단 Plane 1(DriverUiIviStage) 위에 상단 Plane 2(HarSafetyStage)를 오버레이
7. Heartbeat Watchdog & RPC 유사 (Similar) VM 간 RPC(HeartbeatRequest) 타임아웃 감지 시 HAR가 불투명 모드로 전환 시뮬레이터 HUD의 Kill IVI (Crash) 토글이 Heartbeat 단절(iviFaultActive = true)을 트리거하여 즉시 Failover 재현
8. HAR 실행 OS 및 그래픽 렌더러 차이 (Different) Non-Android VM (SDV Media VM) 위에서 순수 Rust 앱 + Impeller 렌더러로 구동 단일 Android 에뮬레이터 환경 제약상 Android 프로세스 내 DesignCompose Squoosh (Compose Canvas) 렌더러로 구동
9. 차량 신호(CAN) 및 Safety Monitor 차이 (Different) PAL이 실제 차량 CAN 신호를 수신하고, MISRA-C Safety Monitor가 픽셀 출력 검증 ClusterDualVmSimulator.kt가 60fps 연속 속도/RPM/경고등 신호를 시뮬레이션하여 주입

2-2. 왜 코드를 두 파일(Stage vs Simulator)로 분리했는가?

Tech-Talk 코드 명확성

발표에서 청중이 "양산과 동일한 순수 .dcf 바인딩 영역"과 "단일 Android 환경 제약을 극복하기 위한 시뮬레이터 영역"을 한눈에 구분할 수 있도록 파일을 엄격히 분리했습니다.

① ClusterDualVmStage.kt (순수 .dcf 바인딩) 양산 모델과 동일

일반 Jetpack Compose UI 위젯(Box, Row, Text, Canvas)을 단 하나도 import하지 않는 순수 선언부입니다. 특히 HarSafetyStage는 Non-Android VM에서 동작하는 HAR의 제약을 반영해 오직 스칼라 데이터와 Variant만 받습니다. 

@DesignComponent(node = "#HAR-stage")
fun harStage(
    // 서브트리 교체 (Variant): 레이아웃/래퍼 전환
    @DesignVariant(property = "#har-variant")
    harVariant: ClusterHARVariant.HarVariant,
    @DesignVariant(property = "#wrapper-variant")
    wrapperVariant: ClusterHARVariant.WrapperVariant,

    // Heartbeat Failover 제어 (#heartbeat=off 배경)
    @Design(node = "BackgroundLayer")
    showFallbackBackground: Boolean,

    // 연속 스칼라 데이터 (CAN 텔레메트리)
    @Design(node = "#driving/speed") speed: String,
    @Design(node = "#driving/speedo-gauge") speedGauge: Meter,
    @Design(node = "#telltale/abs") abs: Boolean,
    // ... (@Composable 교체 람다 0개!)
)
② ClusterDualVmSimulator.kt (환경 제약 시뮬레이터) Hypervisor + CAN 대행

단일 Android 앱 안에서 ① Hypervisor 2-Plane 하드웨어 합성기, ② 60fps CAN 신호 발생기, ③ Heartbeat 장애 주입기 역할을 대신 수행하는 하네스입니다. 

// Hypervisor Display Controller의 2-Plane 합성 시뮬레이션
Box(modifier = Modifier.requiredSize(1920.dp, 720.dp)) {
    // Plane 1 (Bottom Layer): Guest VM 1 - Android DriverUI
    if (!iviCrashed) {
        DriverUiIviStage(panel1, panel2, panel3, ...)
    }

    // Plane 2 (Top Overlay): Guest VM 2 - HAR Safety Stage
    // #HAR-stage는 기본 투명(alpha=0)이므로 하단 Plane 1이 투과됨!
    // iviCrashed == true이면 BackgroundLayer가 켜지며 단독 동작
    HarSafetyStage(
        telemetry = telemetry.copy(iviFaultActive = iviCrashed),
        harVariant = harVariant,
        wrapperVariant = wrapperVariant,
    )
}

2-3. 시뮬레이션 검증 ①: HAR의 Data-Driven 서브트리 교체 (@DesignVariant)

Composable 교체 없이 데이터만으로 UI 트리 전환

HAR에는 Jetpack Compose 코드가 없는데 어떻게 원형 게이지(Retro), 3분할 슬림 뷰(Thin), 후방 카메라 뷰(ModernCamera)로 화면 구조가 바뀔까요? 정답은 .dcf 파일 안에 모든 레이아웃 서브트리가 미리 직렬화되어 있고, 런타임에는 #har-variant라는 Enum 데이터 하나만 바꿔서 트리를 교체하기 때문입니다. 트리가 통째로 바뀌어도 내부의 데이터 홀더(#driving/speed = "34")는 모든 Variant 트리에 동일하게 존재하므로 34 MPH 데이터가 그대로 유지됩니다.

① HarVariant.Retro + Full

듀얼 원형 아날로그 바늘 게이지에서도 #driving/speed = 34 바인딩 유지

② HarVariant.Thin + Thin

3-Panel 미디어/내비게이션 확보용 슬림 레이아웃에서도 동일하게 34 MPH 표시

③ HarVariant.ModernCamera + Full

후방 카메라 뷰포트가 포함된 서브트리로 즉시 전환되며 34 MPH 유지

2-4. 시뮬레이션 검증 ②: 1부 공식 문서의 Alpha See-Through & Heartbeat Failover 재현

AOSP 공식 합성 시나리오 100% 재현

1부 공식 문서의 "Blend HAR and DriverUI output" 및 "RPC theme change" 다이어그램과 똑같은 동작을 단일 CuF1b1eAIukB6YszX6B5OZ.dcf로 검증한 결과입니다.

① Heartbeat ON (정상 See-Through · Dark)

상단 #HAR-stage의 배경이 투명(alpha = 0.0)하여 하단 #android-stage의 Media · Call · Navigation 카드가 자연스럽게 투과됩니다.

② Variable Mode 동시 전환 (Light Theme)

1부 공식 문서의 RPC 테마 동기화 그림처럼, Figma Variable Mode를 Light로 바꾸면 HAR 게이지와 DriverUI 카드가 동시에 밝은 테마로 전환됩니다.

③ Heartbeat OFF (Android IVI Crash Failover)

DriverUI가 중단되면 #HAR-stage 내부의 BackgroundLayer(#heartbeat=off)가 불투명하게 켜지며, 속도계(69 MPH)와 경고등이 끊김 없이 단독 동작합니다.

🎯 Tech-Talk 결론 (Key Takeaways)

  1. AOSP 공식 SDV Display Safety의 핵심은 디자이너가 작업한 단 하나의 Figma 문서(.dcf)를 가지고 Safety VM의 HAR(Rust + Impeller), Android VM의 DriverUI(DesignCompose), 그리고 Safety Monitor(ASIL-B 검증기)를 일관되게 구동하는 것입니다.
  2. 비록 일반 Android 개발 환경에서는 Hypervisor와 별도 Guest VM을 직접 띄울 수 없지만, 본 POC를 통해 단일 .dcf 기반의 2-Stage 분리(#HAR-stage / #android-stage), Rust dc_layout 엔진, HAR의 100% Data-Driven 렌더링(스칼라 + Variant 트리 스왑), 그리고 Heartbeat 기반 Native See-Through 합성까지 양산 아키텍처의 핵심 메커니즘을 그대로 검증할 수 있음을 확인했습니다.
